# 1CDB2SRC

Версия **0.3.0-rc.8** — ускоренный Docker-маршрут включается явно; рекомендуемые
параметры приведены ниже. По умолчанию сохранён прежний `--docker-mode host`.
Поддержка форматов и ограничения конвертера остались от 0.2.0, включая проверенную
обратную загрузку основной конфигурации Документооборота на 8.3.27.

История Git очищена 26.10.2026. Если у вас есть старый клон, клонируйте
репозиторий заново; подробности — [HISTORY.md](HISTORY.md).

## На основе ibcmd-rs

Преобразование CF → XML выполняет доработанный **[ibcmd-rs](https://github.com/Untru/ibcmd-rs)**
автора **[Untru](https://github.com/Untru)**. Спасибо автору за основу конвертера.
Исходный проект распространяется по MIT; его [лицензия](converter/LICENSE)
и уведомления сохранены. Версия upstream и наши изменения описаны в
[NOTICE.md](NOTICE.md), [provenance.json](provenance.json) и каталоге `converter`.

В 1CDB2SRC добавлены чтение конфигураций из MS SQL/PostgreSQL, выбор поставщика,
сборка двух CF/XML, комплект запуска и проверка результатов. Это самостоятельная
программа с включённым сторонним конвертером; авторство ibcmd-rs принадлежит
его авторам.

Выгрузка конфигурации 1С из базы данных

Краткая инструкция для Windows и Linux.

Программа подключается к MS SQL или PostgreSQL и сохраняет **основную
конфигурацию и выбранную конфигурацию поставщика** в двух видах: CF и каталог
XML с доступными исходниками BSL. Платформа 1С для работы не нужна.

## Что изменилось в этой версии

Унифицированы имена Python-пакета, переменных окружения, контейнеров и меток
под 1CDB2SRC. Исходный проект конвертера и его автор явно указаны выше.
Исправления сетевого чтения MS SQL/PostgreSQL и прежние ускорения сохранены.

В предыдущей версии полный прогон большой ERP на нашем ПК занял **37:27.7**
из MS SQL и **36:45.7** из PostgreSQL. Это исторические измерения: в этой
итерации проверены Windows/Linux тесты и малые CF → две XML; большой экспорт
заново не запускался. Условия и ограничения — [PERFORMANCE.ru.md](PERFORMANCE.ru.md).

## Как это работает

1. **Подключается к СУБД** по указанному адресу, базе и учётной записи.
   Сервер может находиться на этом же компьютере или на другом.
2. **Забирает служебные данные конфигурации** в одной согласованной транзакции.
   Прикладные данные документов и справочников не выгружает.
3. **Собирает основную CF.** Проверяет части файлов, восстанавливает из них
   контейнер конфигурации и сверяет его содержимое с прочитанными данными.
4. **Извлекает CF поставщика.** В сведениях о поддержке находит конфигурацию
   по заданному имени, распаковывает её и проверяет имя и версию.
5. **Преобразует обе CF в XML.** Включённый конвертер извлекает метаданные
   и доступный BSL. Он запускается через Docker либо напрямую в Linux — алгоритм
   один. Python собирает итоговые каталоги и служебный файл состава выгрузки.
   Код BSL не исполняется.
6. **Проверяет результат** по составу, размерам и хешам файлов, сохраняет отчёт
   с временем работы и обнаруженными ограничениями.

## Что подготовить

Выберите режим на компьютере, где будет работать программа:

| Режим | Что требуется |
|---|---|
| Windows | Windows x64, Python 3.13, Docker Desktop с Linux containers |
| Linux с Docker | Linux x86-64/glibc, Python 3.13, Docker CLI и локальный Docker Engine |
| Linux без контейнера | Linux x86-64/glibc и Python 3.13; Docker не нужен |

Для Linux нужны доступный `/proc` и поддержка `pidfd_open`, `pidfd_send_signal`
и `prctl` — они используются для контроля и завершения собственных процессов.

В быстром режиме лимит памяти не задаётся. Сохраняются ограничение CPU,
тайм-ауты и очистка собственных процессов и контейнеров. В прежнем режиме
действует лимит конвертера 8 ГиБ и проверка 2 ГиБ резерва; `--profile small`
выбирает лимит 3 ГиБ.

`--capture-seconds` задаёт предел чтения СУБД, включая предел отдельного
SQL-запроса; по умолчанию 600 секунд. Для большой базы или медленного
соединения можно явно указать, например, `--capture-seconds 1800`.

Конвертер и зависимости включены в комплект. СУБД может быть на другой машине;
устанавливать на сервер базы программу или Docker для сетевого подключения не нужно.

Для подключения понадобятся: тип СУБД, адрес, порт, имя базы, логин, пароль
и **имя конфигурации поставщика**, например `УправлениеХолдингомERP`.
Нужны доступ к порту СУБД и права чтения конфигурационных таблиц и системных
метаданных. Указывайте адрес СУБД, а не адрес кластера 1С с портом 1541.

## Запуск в Windows

**1. Скачайте репозиторий** через Code → Download ZIP и распакуйте, например
в `D:\Tools\1cdb2src`, либо клонируйте его в этот каталог.
Приложение находится в папке `app`.

**2. Один раз установите зависимости.** Откройте PowerShell:

```powershell
$tool = 'D:\Tools\1cdb2src\app'
py -3.13 -m venv "$tool\.venv"
& "$tool\.venv\Scripts\python.exe" -m pip install --no-index --find-links "$tool\wheels" --require-hashes -r "$tool\requirements.txt"
```

Зависимости и Docker-конвертер уже входят в комплект; скачивать их из интернета
программа не будет.

**3. Укажите параметры своей базы.** Пример для MS SQL:

```powershell
$provider = 'mssql'                 # Для PostgreSQL: 'postgresql'
$dbHost = 'sql.example.local'       # Для локальной СУБД: '127.0.0.1'
$dbPort = 1433                     # Для PostgreSQL обычно 5432
$database = 'Infobase'
$dbUser = 'export_reader'
$supplier = 'УправлениеХолдингомERP'
$output = 'D:\Exports\run-001'      # Новый, ещё не существующий каталог
```

**4. Запустите выгрузку** и введите пароль по запросу:

```powershell
& "$tool\.venv\Scripts\python.exe" "$tool\export_1c.py" `
  --provider $provider --host $dbHost --port $dbPort `
  --database $database --user $dbUser --prompt-password `
  --supplier $supplier --output $output
```

В Windows по умолчанию используется Docker Desktop. Для PostgreSQL измените
параметры на шаге 3. Для MS SQL пример использует TCP и SQL-логин. Дополнительный
локальный вариант через ODBC/shared memory сохранён: нужен ODBC Driver 17,
`--mssql-driver pyodbc --transport lpc --host localhost --auth integrated`
вместо TCP и параметров SQL-логина.

## Запуск в Linux

**1. Клонируйте репозиторий** или распакуйте Download ZIP в `$HOME/tools/1cdb2src`.
Установите зависимости в отдельное окружение:

```bash
tool="$HOME/tools/1cdb2src/app"
python3.13 -m venv "$tool/.venv"
"$tool/.venv/bin/python" -m pip install --no-index \
  --find-links "$tool/wheels-linux" --require-hashes -r "$tool/requirements-linux.txt"
chmod +x "$tool/runtime/local/ld-linux-x86-64.so.2" "$tool/runtime/local/ibcmd-rs"
```

**2. Выберите способ запуска конвертера и выполните команду.** Пример без
контейнера, с PostgreSQL:

```bash
"$tool/.venv/bin/python" "$tool/export_1c.py" \
  --runtime native \
  --provider postgresql --host pg.example.local --port 5432 \
  --database Infobase --user export_reader --prompt-password \
  --supplier 'УправлениеХолдингомERP' --output "$HOME/exports/run-001"
```

Для обычного Docker Engine замените `--runtime native` на
`--runtime docker --docker-socket /var/run/docker.sock`. У пользователя должен
быть доступ к этому локальному сокету. Docker Desktop не требуется. Если ваш
Engine использует другой локальный сокет, укажите его путь; удалённый Docker daemon
этим выпуском не поддерживается.

Для MS SQL укажите `--provider mssql`, его адрес и TCP-порт. База, учётная запись
и имя поставщика также заменяются своими значениями. Для локальной СУБД используйте
`127.0.0.1`. Нативный конвертер использует свои включённые библиотеки, системные
библиотеки не заменяет. Ни для установки в домашний каталог, ни для native-запуска
root не требуется.

## Быстрый режим Docker

К обычной команде с параметрами базы и поставщика добавьте:

```text
--docker-mode fast --assembly-mode adopt --docker-transfer stream --readback-workers 8
```

Каждая CF один раз переносится в собственный Linux volume. Конвертер извлекает
метаданные и BSL, Python там же формирует служебные файлы и собирает XML.
Готовые каталоги передаются на ваш компьютер TAR-потоком; программа затем
независимо читает и проверяет все файлы. Приложенные CF, XML и BSL не исполняются.
Выбор поставщика и получение CF из СУБД одинаковы в обоих режимах.

Нужен локальный Docker: Docker Desktop с Linux containers в Windows либо
обычный Docker Engine в Linux. Helper-образ включён в комплект; при первом
запуске он загружается из проверенного локального архива. Интернет и сборка
образов при работе не требуются. Сама СУБД может находиться на другом сервере.

`--docker-transfer copy` использует обычный Docker copy вместо TAR-потока.
По умолчанию сохранён прежний маршрут `--docker-mode host`; для него отдельно
доступна сборка `--assembly-mode adopt`, без создания второй копии дерева.
Linux без контейнера по-прежнему запускается с `--runtime native`.
Ошибки не включают другой маршрут автоматически; повторный запуск требует
нового выходного каталога. Известные ограничения формата XML остаются прежними.

### Перекрытие этапов

В fast-режиме с `--assembly-mode adopt --docker-transfer stream` доступны:

| Параметр | Что выполняется одновременно |
|---|---|
| `--side-scheduling sequential` | Последовательная работа, по умолчанию |
| `--side-scheduling transfer-overlap` | Передача основной XML и обработка поставщика |
| `--side-scheduling verify-overlap` | Дополнительно полная проверка основной XML во время обработки поставщика |

В `verify-overlap` перед принятием результата все файлы основной XML читаются
ещё раз и сверяются по SHA; повторно разбирать XML не нужно лишь при точном
совпадении байтов и подтверждённом происхождении ранней проверки. Два конвертера
одновременно не запускаются. Ошибка/отмена останавливает все связанные задачи;
очистка следует после подтверждённого закрытия процессов.

Для перекрытия требуются четыре свободных CPU на компьютере запуска и два в
Docker; память не лимитируется. Перекрытие генерации для native и `--docker-transfer copy` не поддержано.
В fast copy отдельно доступна параллельная заключительная проверка. CF-перенос `--docker-cf-transfer copy` поддержан отдельно.

В предыдущем0.3.0-rc.4 на Документообороте verify-overlap дал 6:14 вместо 6:41 (около7%) в одном сравнении
на загруженном компьютере. Это не гарантия скорости; большой ERP-экспорт этим
режимом пока не проверен. Подробные границы измерений — RELEASE-NOTES.ru.md.

### Параллельная заключительная проверка

Для проверенного сочетания добавьте к команде fast:

```text
--side-scheduling verify-overlap --final-verification parallel --readback-workers 8
```

Также нужны `--assembly-mode adopt --docker-transfer stream` из fast-примера
выше. Именно это сочетание использовалось в замерах ниже. Параллельная final
проверка реализована и для других fast-сочетаний, но ускорение там не проверено.

После получения двух XML основная проверяется двумя потоками, поставщик —
шестью. Общий бюджет8 и два CPU сохраняется. Пулы4/1 для этого режима
отклоняются. По умолчанию проверка последовательная; native не поддержан.

CF/профили/происхождение проверяются, все файлы читаются заново. В сочетании
с `verify-overlap` основная сверяется с подтверждённой ранней полной XML-проверкой;
поставщик проходит полный разбор XML. Общий успех требует закрытия обеих
успешных проверок. Ошибка/отмена не даёт частичного успеха.

На Документообороте весь путь от сохранённых CF до двух проверенных XML:
последовательно 6:48.2, с2+6 — 6:33.6
и 6:10.2. Все46786файлов/11774доступныхBSL совпали.
Новое чтение СУБД в этих замерах не включено. ERP новым режимом не проверялся;
на другом диске или при другой нагрузке результат может быть хуже.
Подробные границы — RELEASE-NOTES.ru.md.

### Дополнительный способ переноса CF

`--docker-cf-transfer copy` (по умолчанию) использует обычный Docker copy.
В fast Docker можно явно добавить `--docker-cf-transfer bind-copy`: helper
читает один CF через привязку только для чтения, копирует его в собственный
Linux volume и проверяет записанные байты повторным чтением. Это параметр
входного CF; `--docker-transfer stream` отдельно управляет переносом готового XML.

Файл должен быть доступен helper для чтения с учётом сопоставления UID в Docker.
Универсальная поддержка Linux-файлов 0600 и rootless-сред не подтверждена.
Права исходного файла не меняются, автоматического fallback нет. При отказе
доступа выберите `copy` и новый каталог результата. Остальные режимы сохранены.

## Где результат

Выходной каталог должен быть новым. Для MS SQL по умолчанию нужен уже включённый
SNAPSHOT. Если допустимы блокировки чтения, явно добавьте
`--mssql-consistency serializable`: это может задерживать запись других
пользователей. Настройки сервера программа сама не меняет.

В указанном каталоге появятся:

```text
main.cf          Основная конфигурация
vendor.cf        Выбранная конфигурация поставщика
main/xml/        XML и доступный BSL основной конфигурации
vendor/xml/      XML и доступный BSL поставщика
report.txt       Краткий итог, время и ограничения
report.json      Подробный отчёт
_work/           Промежуточные данные для диагностики
```

`COMPLETE` означает завершённую выгрузку; `COMPLETE_WITH_LIMITATIONS` — выгрузку
с перечисленными в отчёте ограничениями. При `FAILED` результат частичный:
причину ищите в отчёте. Для повторного запуска задайте новый выходной каталог.

## Версия платформы и формат XML

Режим совместимости конфигурации (например, 8.3.24), версия её внутреннего
хранения и целевая версия XML — разные характеристики.

`--platform auto` выбирает профиль отдельно для каждой CF: поддержанные старые
корни 67/68 → профиль 8.3.27/XML 2.20; корень 76 → 8.5.1/XML 2.21. Это выбор
поддержанного представления, а не определение версии вашей установленной платформы.
Можно явно указать `--platform 8.3.27` или `--platform 8.5.1`; второй профиль
может читать поддержанные старые корни. Понижение нового корня до старого
профиля отклоняется. Один явный профиль применяется к обеим CF.

Для проверки обратной загрузки используйте ту же версию платформы, под которую
сформирована XML. Для основной конфигурации Документооборота подтверждена цепочка
CF → XML 2.20 → загрузка на 8.3.27 → сравнение с исходной без отличий.
При загрузке той же XML на 8.5 были массовые отличия свойств форм; обратная
совместимость для этого сценария не подтверждена. Выбор `--platform 8.5.1`
сам по себе не является гарантией чистого сравнения на 8.5. Не меняйте вручную
атрибут версии XML и режим совместимости ради устранения отличий.

## Границы первой версии

CF собираются с проверкой содержимого. **XML пока экспериментальный:** известны
расхождения со штатной выгрузкой в формах и отдельных свойствах метаданных.
Четыре проверенных расхождения порядка прав исправлены общим правилом для
Catalog/InformationRegister и включены в этот комплект. В проверенной большой
конфигурации остаётся одно расхождение формы: маркер `~` у поля `ЭтоГруппа`
в UseAlways и связанная с ним позиция поля. Код BSL это не меняет;
при сравнении XML такое отличие может выглядеть как доработка. Версия XML
и свойства совместимости также могут отличаться от исторической штатной
выгрузки. Полного равенства произвольной выгрузке пока не обещаем.
Закрытый код программа не восстанавливает; неизвестный формат может вызвать отказ.

В 0.2.0 также исправлены чтение старых корней конфигурации, нескольких назначений
приложения, наследуемого шрифта формы, сохранение современной бинарной подписи
без пересоздания и проверка длинных путей Windows. У поставщика Документооборота
в XML 2.21 остаются два макета СКД с иным представлением картинок: байты PNG
сохранены внутри XML, но отдельный файл картинки не создаётся. В одной форме
возможна иная запись пустых локализованных подписей; на проверенной основной
8.3.27 это не дало отличий конфигураций. Полный набор доступных BSL и файлы прав
на проверенном Документообороте совпали с контрольными выгрузками.

Большие конфигурации требуют больше времени и памяти. Native запускается без
контейнерной изоляции: действует лимит адресного пространства каждого процесса
и периодическая проверка суммарной памяти. Это не жёсткий общий лимит cgroup.
Linux проверен на x86-64 в WSL: полные запуски под root, отдельно конвертация
одной CF под обычным UID без root. Совместимость
со всеми дистрибутивами, ARM и musl не заявляется. Сетевой MS SQL с логином/паролем
проверен полным запуском на Windows с удалённой СУБД; Linux native с таким подключением отдельно не проверялся. Отдельных параметров TLS
и сертификатов в CLI пока нет.

На маленькой PostgreSQL-базе полный запуск занял **25,40 с** в Linux native,
**31,23 с** в Linux Docker и **14,32 с** в Windows Docker. Это время всего
конвейера на стенде, не прогноз для вашей базы.

## Исходники и тесты

Python-код находится в `app/onecdb2src`, исходники конвертера — в `converter`.
Происхождение и сборка описаны в [BUILD-AND-TEST.ru.md](BUILD-AND-TEST.ru.md),
лицензии — в [NOTICE.md](NOTICE.md). Переносимые тесты из корня репозитория:

```powershell
app\.venv\Scripts\python.exe -B -m unittest discover -s tests -v
```

В Linux используйте `app/.venv/bin/python -B -m unittest discover -s tests -v`.
Тесты работают с синтетическими данными, подключения к СУБД не требуют.
